# 01_封面

这次汇报介绍我围绕 Vortex 三点零 Command Processor 完成的优化实验。重点不是逐条展示修改，而是解释为什么选择这些优化、RTL和Runtime中怎样实现、实验结果意味着什么，以及它们如何为后续多队列研究建立基础。

---

# 02_研究问题

整项工作的主线可以归纳为四个问题。第一，为什么 CP 会成为值得研究的前端；第二，瓶颈究竟来自执行状态、取指流量还是存储延迟；第三，如何证明性能变化没有破坏命令语义；第四，面对面积和频率代价，哪些优化值得默认集成。后面的内容都围绕这四个问题展开。

---

# 03_CP架构

先看 CP 在系统中的位置。Host 通过 AXI-Lite 配置队列和 Ring，每个队列的命令经过 Fetch、Unpack 和 Engine，再竞争 KMU、DMA、DCR 和 Event 等共享资源，最后由 Completion 更新序号。因为这是一条串联路径，所以前端多等待一个周期，可能直接推迟后面的 Kernel 启动或数据操作。

---

# 04_Baseline瓶颈

Baseline 的第一项重要结论是，当前单队列场景的主要矛盾不是仲裁。所有测试的 arb wait 都是零，而 B2 的 DCR 响应等待达到八十周期，B7 的 KMU 等待达到六十四周期。与此同时，Engine仍有固定状态开销，Fetch也存在带宽和延迟问题，因此我把优化拆成执行路径、命令布局和读取流水三个层次。

---

# 05_实验方法

为了避免只得到一组孤立数字，所有实验都采用同一流程：先建立 Baseline，再定位原因，然后参数化实现，之后做边界和压力验证，最后结合 PPA 决定是否集成。评价指标同时覆盖 CPC、吞吐、取指字节、序号以及面积和频率。实验三也提醒我们，DMA尾拍越界已经被证明，但没有完整内存域和Ring链路时，不能把它扩大解释成真实命令Ring被覆盖。

---

# 06_FastPath实现

实验四处理的是 Engine 的固定控制开销。NOP 不需要申请任何共享资源，原来的 DECODE 状态对它实际上只产生一次无效跳转，所以我增加参数 ENABLE_NOP_FAST_PATH，在 IDLE 中识别 NOP 后直接进入 RETIRE。其他命令仍然经过原来的 DECODE、BID 和 WAIT DONE 路径，并且参数默认关闭，保证实验实现不会悄悄改变整机默认时序。

---

# 07_FastPath结果

Fast Path 把 NOP 的 CPC 从三点零降到二点零，改善三分之一，执行吞吐从零点三三三提高到零点五。三种压力规模都保持序号正确，没有丢失和重复。但是模块级时序代理显示 Fmax 下降百分之六点四三，超过设定的重新评估线。因此结论不是简单接受，而是功能接受、默认集成拒绝，这说明控制周期收益必须和关键路径一起看。

---

# 08_Packing实现

实验五针对的是缓存行利用率。DCR 写命令只有二十字节，如果每条命令独占六十四字节缓存行，就会浪费超过三分之二的读取带宽。Runtime 因此增加缓存行构建器，在空间足够时继续追加命令，空间不足或批次结束时补零并刷新。更关键的是把 tail 和 expected seqnum 分开：tail 按缓存行增长，序号仍然按命令增长。

---

# 09_Packing结果

Packing 把一千条 DCR 命令需要的缓存行从一千条降到三百三十四条，平均取指字节从六十四降到二十一点三七六，流量下降百分之六十六点六。总周期仍然是七千零十一，这不是实验失败，而是说明当前负载的瓶颈在 DCR 执行和退休，Fetch流量已经能够被重叠。它的价值在于降低未来高延迟和多队列环境中的前端压力，并为预取提供更高的单行命令密度。

---

# 10_Prefetch实现

实验六进一步处理 Host AXI 延迟。原始 Fetch 必须等待当前缓存行返回并消费完，才能请求下一行；新设计把请求、响应缓存和消费拆开，用 fetch head 表示已请求位置，用 head 表示已消费位置，中间加入两项缓存行 FIFO。容量判断同时计算已返回行和在途请求，保证每个未来响应都已经预留槽位，同时仍保持有序响应，不引入重排结构。

---

# 11_Prefetch结果

预取的收益随着 AXI 延迟增加而迅速接近两倍。延迟一个周期时吞吐提升约百分之四十八点八，延迟二十周期时提升百分之九十九，延迟一百周期时达到百分之九十九点八。这里没有降低 AXI 本身的延迟，而是把下一行的等待和当前行命令输出重叠。所有点都保持六十四次读取、一百九十二条命令以及零丢失零重复。

---

# 12_正确性验证

三项优化改变的对象不同，所以验证也不能只看一次 PASS。Fast Path 要确认状态跳转和资源分类，Packing 要确认变长命令、空间不足和 Ring 回绕，Prefetch 要确认在途请求、FIFO容量和返回顺序。最终共同的不变量是命令数量、顺序、序号以及完成语义都不能改变，这也是后续优化必须继续复用的验证框架。

---

# 13_PPA决策

综合三项实验，可以看到性能数字不能脱离适用场景和 PPA。Fast Path 的周期收益明确，但频率代价使它默认关闭；Packing 显著降低流量，但在当前 DCR 负载中不改变吞吐；Prefetch 在高延迟场景接近两倍吞吐，但 ASIC 面积增加百分之十点八七。因此当前采用参数化保留能力、默认配置保持保守的集成策略。

---

# 14_后续研究

这些实验对后续研究最大的影响，是已经建立了可复用的指标、延迟模型、参数开关和正确性检查。下一步可以在此基础上研究 Priority-aware 仲裁、Aging 防饥饿和 Event Wait 公平性，再推进多队列与 QMD 式启动。系统层还需要测量 Packing 与 Prefetch 的组合收益，并补齐 SimX 与 RTL 周期一致性以及 XRT 全链路验证。

---

# 15_总结

最后总结三点。第一，CP瓶颈是分层的，不能用单一吞吐指标解释；第二，Fast Path、Packing和Prefetch分别优化执行、数据布局和取指等待；第三，正确性、性能与PPA必须共同决定集成。下一阶段的研究重点应从单队列局部优化，转向多队列资源竞争、组合优化和端到端模型一致性。
